# B站清澈人声、音量增强与动态音量平衡

> **开发背景与 AI 声明**
>
> 由于本人在 B站观看视频时，比较依赖 B站官方的音频增强功能。2025 年的某个月，不知出于什么原因，这项功能从所有视频播放器中消失了。
>
> 在经历了一年多的等待后，目前依然没有再次用上这项功能，因此我决定借助 AI 编写一个功能相近的脚本。
>
> **以下介绍及脚本代码均由 AI 生成。**

这是一个面向 Bilibili 网页播放器的音频增强脚本，主要用于改善视频音量偏小、人声不够清楚，以及不同视频或不同说话者之间音量差异过大的问题。

所有音频处理均在浏览器本地通过 Web Audio API 完成，不会上传音频或收集播放记录。

## 主要功能

### 清澈人声

提供三种人声预设：

- **A 轻柔**：较自然、处理感较弱，适合已经比较清楚的人声。
- **B 原生**：按照 B站原生“清澈人声”的风格调校，兼顾清晰度与响度。
- **C 强化**：进一步突出人声存在感，适合录音偏闷或背景声较重的视频。

每次打开新视频时，清澈人声默认关闭，不会自动沿用上一个视频的选择。

### 音量增强

可在 **-12 dB 至 +12 dB** 范围内手动调节音量，步进为 0.5 dB。

适合整体录音音量偏小或偏大的视频。每次打开新视频时，手动音量增强会恢复为 0 dB。

#### 滚轮 / 方向键音量增强（最高 1000%，仅网页全屏 / 全屏）

滚轮调音量的默认开关是**开启**（可在油猴菜单的「滚轮/方向键调音量默认」中关闭，该选项会保存为默认配置，之后打开新视频同样生效）；除此之外，脚本只在播放器处于**网页全屏或全屏模式**时才接管滚轮和上下方向键。

两个前提都满足时，鼠标位于**播放器任意位置**（画面、覆盖层或控制栏）时，滚轮均可调节音量；上下方向键同样可以调音量（与 B站 原生按键位置一致），最高 **1000%**（约 +20 dB）。Ctrl / Command 加滚轮不会被脚本接管。

普通、宽屏、小窗等模式下脚本**完全不拦截事件**，也不阻止页面滚动，音量完全交给 B站播放器自己的逻辑处理（方向键则由 B站 与页面按原生方式处理）。模式判定依次为：浏览器全屏 API（`document.fullscreenElement` 等）→ B站播放器的 `data-screen` 属性（`web`=网页全屏、`full`=全屏）→ 播放器/页面类名兜底 → 播放器是否铺满视口兜底；如果以上都判断不出沉浸模式，按「不接管」处理。

- **0%–100%**：滚轮每次滚动增减 **1 个百分点**，上下方向键每次按键增减 **5 个百分点**，均由脚本直接调节视频音量。
- **100%–1000%**：向上滚动或按上键每次按 **1.1 倍**递增，向下按相同比例递减。降回 100% 后，继续向下即可调低普通音量，最低 0%。
- **静音时**：向上滚动或按上键从 0% 起步恢复声音（滚轮 +1%、方向键 +5%），并清除残留增幅。
- **长按方向键**：自动重复会限流（约每 90 ms 一档），避免音量或增强倍率瞬间被拉飞。

滚轮或方向键调节时，播放器中央显示半透明的「扬声器图标 + 当前百分比」提示，覆盖 0%–1000%。连续调节会刷新数值，停止约 1 秒后自动隐藏；支持全屏显示。

由于浏览器不允许 `video.volume` 超过 1.0，超出 100% 的部分通过音频处理链中的增益节点实现。B站原生音量滑块最多到 100%，脚本会尝试同步面板数字，当前增幅也会显示在播放器左上角状态栏「音量增强」和音频增强面板中。

「高增益防削波」**默认开启**，在增强超过 100% 时启用限幅器以减轻削波，可在油猴菜单中关闭；动态音量开启时由动态音量自己的限幅策略接管。已保存的用户开关选择会继续保留。

在音频增强面板里点击增幅数值可立即重置为 100%。每次打开新视频时，滚轮增强会重置为 100%。

#### 直播间（live.bilibili.com）

直播间播放器与视频页不是同一套：播放器根是 `#live-player-ctnr` / `#live-player`，控制栏由播放器 SDK 运行时创建（Svelte 版），**只在鼠标进入播放器底部时挂载、鼠标离开约 4s 后整棵卸载**。

按钮的插入方式与视频页一致：**把两个按钮作为控制栏自己的子节点插进去**，随控制栏一起显隐；区别是插入位置与触发时机：

- **插在哪**：控制栏内 `.left-area` 的「**音量按钮之后、开播时长之前**」（控制栏内部类名带 `svelte-xxxx` 编译哈希，因此只用不带哈希的语义类定位）。官方预留的空扩展位 `.right-area > .ext-nodes` 作为兜底。按钮作为控制栏自己的 flex 子项参与排版，不做绝对定位、不测坐标，因此不会压住原生控件，也不会随窗口尺寸 / 进出全屏失位。
- **为什么不「找锚点 + 绝对定位」**：控制栏未挂载时，那颗「最靠右的原生控件」其实是「点击取消静音」浮层，会把按钮插到错误的层里、定位失效 —— 这是 1.15.4–1.15.7 反复失败的根因，1.15.8 已彻底移除这套方案。
- **什么时候插**：控制栏挂载的那一刻**同步**插入（MutationObserver 回调里完成）。晚一帧插入的话，控制栏会先按「没有按钮」的布局画一帧、下一帧再把开播时长挤开一次，看起来就是「控制栏弹出来时抖一下」。

沉浸模式（直播间里叫**网页模式 / 全屏模式**）实测**不会改** `#live-player-ctnr` 的类名（用 MutationObserver 盯着，全程不变），真正的信号是播放器对 `#fullscreen-container` 请求了**元素全屏**（`document.fullscreenElement` 非空）；这样普通模式就不会被误判成沉浸模式，滚轮与方向键仍交还 B站 原生逻辑。浏览器全屏 API 的判断依然优先。

### 动态音量平衡

脚本会持续检测当前响度，在 **-12 dB 至 +12 dB** 范围内自动补偿，尽量减小不同视频、不同说话者和不同片段之间的音量差异。

提供三档目标响度：

- **舒适：-16 LUFS**，适合长时间观看。
- **标准：-14 LUFS**，兼顾响度与舒适度。
- **响亮：-12 LUFS**，适合本身音量明显偏小的视频。

动态音量在首次安装时默认关闭。可以在油猴菜单中设置新视频默认开启或关闭，并选择默认目标响度。

> 说明：脚本用简化的 K-weighting 近似滤波（高架 + 高通）和 30–100 ms 的短块统计响度，显示的数值属于**近似 LUFS**，与专业响度计（ITU-R BS.1770）的读数可能存在 1 LU 左右偏差，仅作为自动补偿的相对参考。

## 五档响应速度

- **极速**：适合多人游戏语音、发言者频繁切换的内容。
- **快速**：适合多人对话、直播连麦和访谈。
- **均衡**：适合单人讲话但偶尔远离麦克风的内容，也是默认档位。
- **平缓**：适合教程录制、长时间解说等音量变化较少的内容。
- **慢速**：适合整体音源稳定、希望尽量减少处理感的内容。

响应越快，越能及时跟随短时间的音量变化；响应越慢，听感通常越平稳自然。建议先使用“均衡”，再根据视频类型调整。

## 使用方法

1. 打开任意 Bilibili 视频页面。
2. 播放器音量按钮左侧会出现两个功能按钮（直播间为**控制栏内、音量小喇叭与开播时长之间**）：
   - 音频增强：调节清澈人声和手动音量增强。
   - 动态音量：调节自动响度平衡、目标响度和响应速度。
3. 也可以在播放器画面上点击右键，从 B站原生右键菜单进入对应功能。
4. 把播放器切到**网页全屏或全屏**（直播间里叫**网页模式 / 全屏模式**），鼠标停在播放器任意位置滚动滚轮，或按上下方向键，即可调节 0%–1000% 音量（滚轮每次 1%、方向键每次 5%），中央会显示当前百分比；普通、宽屏、小窗等模式下音量由 B站 原生逻辑处理。如果不想要脚本接管，可在油猴菜单中关闭「滚轮/方向键调音量默认」（默认开启）。
5. 油猴扩展菜单中可以设置滚轮/方向键调音量的默认开关、动态音量的默认状态、默认目标响度、五档响应速度、状态栏显示方式，以及高增益防削波开关。

## 实时状态栏

启用相关功能后，播放器左上角可以显示：

- 当前响度与动态补偿值。
- 当前动态响应档位。
- 手动音量增强的分贝数。
- 当前清澈人声预设。
- 音量增强超过 100% 时，显示当前倍率（如 `348%`）。

状态栏会跟随播放器控制栏一起显示或隐藏。可以在油猴菜单中关闭状态栏，或将背景不透明度设置为 25%、45%、65% 或 85%。

## 默认行为

- 新视频的手动音量增强默认为 **0 dB**。
- 新视频的清澈人声默认为 **关闭**。
- 动态音量默认关闭，但可以通过油猴菜单改为默认开启。
- 动态音量的目标响度和响应速度会保存到浏览器本地。
- 滚轮/方向键调音量默认 **开启**，但只在网页全屏/全屏模式下由脚本接管（滚轮每次 1%、方向键每次 5%）；可在油猴菜单中关闭，选择会保存到浏览器本地。
- 新视频的音量增幅恢复为 **100%**。
- 高增益防削波默认 **开启**；菜单中已保存的开关选择优先于默认值。

## 注意事项

- 请不要同时启用多个会接管 B站视频音频的油猴脚本，否则浏览器可能拒绝重复创建音频处理链。
- 如果提示视频已被其他音频脚本占用，请停用旧版或其他音频处理脚本，然后刷新页面。
- 浏览器可能要求先点击一次页面或开始播放，之后 Web Audio 音频处理才会启动。
- 动态音量无法单独分离已经混在一起的人声、音乐和游戏声音，它调节的是视频的整体响度。
- 极端增益可能同时放大底噪，建议优先尝试动态音量，再按需要增加手动增益。
- 本脚本为第三方用户脚本，与哔哩哔哩官方无关。

### 1.15.9

- **修复直播间「音频一会有一会无」**（反馈：看直播时声音时有时无）。根因是脚本的「音源接管」会被页面里的**杂项 `<video>`** 触发：实测直播间（无脚本埋点 24s + 事件时间线）——主播放器 `<video>`（866×487、`blob:` MSE）稳定播放且元素不重建，但页面**自己会周期性创建并播放第二个 video**：`0×0`、`display:none`、`muted`、`volume: 0`，`src` 指向 `i0.hdslb.com/bfs/live/bc…`，父节点 `.supportWebp`（B站 自己的功能探测元素），实测 `play` → `waiting` → `playing`（t=47.0s）→ 3 秒后 `pause`。脚本在 document 捕获阶段监听 `play`/`playing`，对该类视频没有任何过滤，于是走了「切换音源」：给探测视频建 `MediaElementSource`，并 **`disconnect()` 掉主播放器的 source**。而 `createMediaElementSource` 是不可逆的 —— 元素一旦被接管，声音就只能经由脚本的音频图输出，source 一断等于**彻底没声**（元素还在播）；直播流又很少再触发 `play`/`playing`，声音就一直回不来，直到某次事件把它切回来 —— 表现就是「一会有一会无」。
- 自动接管新增安全门槛 `shouldAdoptVideo()`：只接管**可见**（`isVisible`：≥30×20、非 `display:none` / `visibility:hidden` / 透明）、**非 `muted`**、**`volume > 0`**、且**当前没有别的视频正在出声**的视频。0×0 静音探测视频、推荐位悬停预览因此再也抢不走音源；用户在播放器上的显式操作（滚轮 / 方向键调音量、点脚本按钮）不走这道门槛，仍按原逻辑直接建链路。
- **切换音源不再 `disconnect()` 旧 source**：保留旧连线，任何被接管过的元素永远留有通往 destination 的通路（同一时刻只有一个视频在出声，Web Audio 对同一对节点的重复连接会被忽略，不会叠加音量）。
- 新增**音源看护** `keepAudioPathAlive()`（1s 一次，页面隐藏或从没用过增强时直接返回）：上下文非 `running` 时 `resume()`（输出设备切换 / 系统挂起能自愈），并把「真正在出声的那个视频」重新接上（元素被页面重建、错过 `play`/`playing`、或开头被自动播放策略静音而用户后来才点「取消静音」时兜底）。
- 音源切换时打一行 `console.info`：「音源已接管：<id> <宽>×<高> volume=… muted=…」，以后再遇到「声音不对」可直接看日志确认接力是否正常。

### 1.15.8

- **拿到直播间控制栏的真实 DOM 后重写注入**（此前 1.15.1–1.15.7 六次都是在没有真实结构的情况下猜的）。实测结论：直播间用的是 Svelte 版播放器，控制栏结构为
  `#web-player-controller-wrap-el > .live-web-player-controller > .control-area`，其中 `.control-area` 下分 `.left-area`（播放/暂停、刷新、`.volume` 音量、开播时长）与 `.right-area`（**全屏模式**、**网页模式**、`.danmaku` 弹幕设置、关闭弹幕、小窗模式、`.quality-wrap` 清晰度、**`.ext-nodes` 官方预留扩展位**）——按钮名取自实测 tooltip，直播间叫「网页模式/全屏模式」，与视频页的「网页全屏/全屏」不是同一套叫法。
- 关键行为：控制栏**只在鼠标进入播放器底部时挂载，鼠标离开约 4s 后整棵卸载**（`#web-player-controller-wrap-el` 未 hover 时 0 子节点）。因此按钮不能一次性插入，改为每次扫描现场查找已挂载的控制栏，挂载了才插 —— 卸载时按钮随控制栏一起消失，下次挂载自动补回。
- 插入位置定在 `.left-area` 内**「音量按钮之后、开播时长之前」**（官方预留的空扩展位 `.ext-nodes` 仅作兜底）：实测左右间距各 4px、与原生控件之间的间距一致，时长会因此整体右移这组按钮的宽度。同时明确不再使用「按位置+尺寸猜最靠右原生控件」的锚点方案：那套逻辑在控制栏未挂载时会把「点击取消静音」浮层当成锚点，导致按钮落在错误的层里、定位失效（这就是 1.15.4–1.15.7 反复失败的根因）。
- 直播间按钮改为**控制栏自己的 flex 子项**，彻底移除绝对定位与 `fx-placed` 门控：不再测量坐标，因此不会压住原生控件，也不会随窗口尺寸 / 进出全屏失位。按钮先放进脚本自己的分组容器再整体插入，间距由脚本决定，不受控制栏内部 `gap` 影响。
- 尺寸对齐原生控件：按钮 30×30（原 34×32）、图标 24×24（原 22×22），与 `.control-area` 内原生按钮一致，并补上 hover 底色与键盘焦点描边。
- `.right-area` 是 `row-reverse`（DOM 顺序 = 视觉从右往左），插入位置按这个顺序理解，避免排到反方向。
- 音量控件补进 `VOLUME_WHEEL_SELECTOR`：直播间的音量是 `div.volume` + 弹出面板 `div.volume-control`（**没有 `input[type=range]`**，只有 `.slider-rail` / `.slider-handle`，读数在 `.number` 里），增强倍率的读数改写因此也能在直播间生效。
- 顺带把直播间的沉浸模式判定实测清楚了（此前只标了「未验证」）：直播间进**网页模式 / 全屏模式都不会改 `#live-player-ctnr` 的类名**（用 MutationObserver 盯着，全程零改动，仍是 `… normal`），真正的信号是播放器对 `#fullscreen-container` 请求了**元素全屏**（`document.fullscreenElement` 非空）。所以 `isImmersivePlayback` 是靠第一条全屏检查命中的，`normal` 那条提前返回并不会拦掉网页模式。实测行为：普通模式下滚轮不被脚本接管（无 OSD，交还 B站 原生逻辑）；进网页模式后滚轮由脚本接管（OSD 出现、音量按 1% 步进、静音按预期解除）。代码里补了注释说明**不要**把「播放器铺满视口」的兜底挪到 `normal` 判断之前：普通模式下窗口又窄又矮时会误判，会抢走 B站 原生滚轮/方向键。
- 顺手修掉插入时机带来的**抖动**与空转扫描（反馈「控制栏弹出来不顺畅」）。① 直播间控制栏是「hover 才挂载」的，挂载本身就是往 `#web-player-controller-wrap-el` 插子节点（Svelte 在文档外拼好再整体插入），所以改为在 MutationObserver 回调里**同步**把按钮插好：实测「按钮出现时刻 − 控制栏挂载时刻」从约 100ms（受 100ms mutation 节流限制）降到 **0.7–1.1ms**，控制栏第一帧就是最终布局，开播时长不会再被挤一下；②「什么都没找到」是直播间的常态，全量扫描加**空扫描指数退避**（150ms → 300ms → … → 1s，插上即恢复全速），`findLiveBarHost` 去掉全文档兜底、改用 `getElementById` 定位：实测空扫描频率降到 **0.48 次/秒**（原先每个 mutation 节流窗口最多一次，约 10 次/秒）。
- 另记一笔性能基线，免得以后误判：这个直播间页面**本身就很重**——无脚本状态下，同样 5 轮 hover 进出循环里页面自己就调了 575 次 `document.querySelector`（其中 495 次是 `[class*=] / [data-]` 这类要逐元素匹配的昂贵查询）和 353 次 `getComputedStyle`。脚本只往控制栏插两个按钮、不重写播放器控制栏；若仍觉得卡，先确认是不是开了「动态音量 / 音量增强」（那条路径跑主线程响度分析，极速档每 30ms 一次）。
